镜像不是进程活着，Readiness 也不是端口打开

今天的胜利目标：你能解释镜像如何生成容器、为什么应用不能以 root 运行，以及 /health 和 /ready 各自回答什么问题。

为什么这对求职重要：面试官说“你这个 Agent 怎么部署”时，答案不能停在“运行 Uvicorn”。企业交付要能说明可复现构建、密钥边界、运行权限、持久化与流量探针。

先分清三个对象

源码仓库

代码、pyproject.toml、uv.lock 与只读种子数据，是构建输入。

镜像 Image

不可变的文件系统模板，包含固定 Python、生产依赖和已安装应用，但不包含本机 .env。

容器 Container

镜像的一次运行实例，拥有进程、临时层、运行配置和挂载卷。

同一镜像可以创建多个容器，但当前 ServiceOps 的 SQLite 状态不能支持随意多副本。交付单元可复制，不代表状态层已经分布式化。

为什么使用多阶段构建

builder: Python + 固定 uv + 下载缓存 + 编译/安装
                 │ 只复制 /app/.venv
runtime: Python + .venv + data/seed + 非 root 用户

构建工具可以进入 builder，但不会进入最终 runtime。这样运行镜像更小、攻击面更清晰，也避免把测试依赖、源码工作区和下载缓存带到生产进程旁边。

两种健康问题不能混在一起

探针回答的问题ServiceOps 行为
/healthHTTP 进程是否还活着？轻量返回 ok，不访问数据库。
/ready现在是否应该接收业务流量？读取 Checkpointer、业务库、Outbox 和审计库，任一失败返回 503。

数据库暂时不可用时，进程仍可能活着并可输出日志。正确动作是先从流量池摘除，而不是把“端口可连接”误当成“Agent 可工作”。

四条运行边界

  1. 非 root：固定 UID/GID 10001，降低依赖漏洞被利用后的权限。
  2. 只读根目录：只有 /app/data/runtime 卷可以保存 SQLite。
  3. 不烘焙密钥：.dockerignore 在构建上下文入口排除 .env。
  4. 单 worker：当前 SQLite 是单节点边界；要横向扩展先迁移 PostgreSQL。

即时判断

判断 1：只要容器 8000 端口能连接，就可以继续把 Agent 请求分给它。
判断 2：当前 Compose 可以证明单机容器交付，但不能证明 SQLite 架构已支持生产多副本。

在代码里找到证据

  1. 打开 Dockerfile，找到 builder/runtime、USER 10001:10001 和单 worker。
  2. 打开 .dockerignore，确认 .env、.venv、data/runtime 不进入构建上下文。
  3. 打开 compose.yaml，找到只读根目录、具名卷、全部 Capability 删除和 /ready。
  4. 安装 Docker 后运行示例 15，观察 liveness、四依赖 readiness 和未认证 401 三层结果。
