Alembic迁移：给数据库结构做版本升级

这里的“迁移”通常不是把数据库搬到另一台机器，而是把表、列、索引和约束从旧版结构安全升级到新版结构。

商场装修类比

应用代码像新版营业方案，数据库像商场。新方案要求增加“退货柜台”和“审计室”，不能让每个店员开门时各拿锤子施工。Alembic把装修步骤写成带编号的施工单，由一支一次性装修队按顺序执行；验收成功，店员才开门营业。

它解决什么问题

没有迁移管理使用Alembic
测试库有新列，生产库忘了加每次结构变化都有版本脚本
多人手工执行SQL，顺序不一致按down_revision → revision依次执行
新版代码先启动，却找不到新表迁移成功成为API启动门槛
不知道数据库现在是哪一版alembic_version记录当前版本

一份迁移脚本里有什么

revision = "20260821_0001" # 本次版本号
down_revision = None # 上一版；None表示第一版

upgrade(): # 向前升级
创建 return_requests
创建 return_outbox_events
创建 approval_audit_events

downgrade(): # 回退；本项目为防止破坏性操作而禁用

以后若要加新列，应新建0002迁移并指向0001，而不是改写已经部署过的0001历史。

upgrade head发生了什么

读取数据库当前revision
→ 找出尚未执行的迁移
→ 按版本链顺序运行upgrade()
→ 更新alembic_version
→ 成功退出；任一步失败则回滚并阻止API启动
当前项目的实际部署顺序

PostgreSQL健康 → 一次性migrate容器运行alembic upgrade head → 成功退出 → 两个Agent API实例才启动。这样不会让两个API副本同时抢着建表。

它不是什么

不是数据库备份删列等高风险操作前仍要备份；迁移脚本不能替代备份。
不是普通业务写入用户创建退货记录是应用业务；建退货表才是结构迁移。
不一定搬业务数据只有脚本明确写了数据转换时才会改存量行。
不管理本项目所有表这里Alembic只管ServiceOps业务表；LangGraph Checkpoint表由官方Saver管理。
记住一个边界

Alembic像“数据库结构的Git历史”，但它不是完整Git，也不是数据快照。它记录并执行结构演进，不能保证你随时无损回到任何数据状态。

一分钟检验

新版代码需要refund_amount列，正确做法是直接修改第一版迁移，还是新增第二版迁移？

查看答案

新增第二版迁移。已经执行过的历史要保持不变，所有环境才能从各自当前版本沿同一条链升级。

面试一句话：Alembic把数据库结构变化写成有顺序、可追踪的版本脚本；部署时先升级到head，成功后再启动API，避免代码与表结构不一致。
