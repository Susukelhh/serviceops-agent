把代码回归门和模型晋级门分开

今天的胜利目标：看到一次失败时，你能先判断它属于“代码/数据回归”，还是“真实模型候选不稳定”，而不是习惯性点重跑。

为什么这对求职重要：杭州 Agent 岗位面试官不只想听“我接了 GitHub Actions”，还会追问大模型有波动时 CI 怎么可信、密钥怎么保护、模型版本怎么晋级。这个项目现在有一套可以指给他看的答案。

一张图记住两道门

门 A：确定性代码回归门

触发：每次 Push / Pull Request

依赖：mock + deterministic + hash + extractive

结论：红灯表示当前提交、黄金标签或硬规则回归。

要求：快、稳定、无密钥、零模型费用。

门 B：真实模型晋级门

触发：开发者手工确认

依赖：真实千问分类、规划、Grounded Generation

结论：红灯表示候选质量或跨轮稳定性不足。

要求：多轮、留证、先跑基线、保护额度。

为什么不能让 PR 直接依赖千问

同一提交可能因为网络、限流、服务商更新或采样波动得到不同结果。若它是唯一合并门，开发者无法区分代码 Bug 和外部波动。ServiceOps 因此让门 A 决定“代码能否继续”，让门 B 决定“某个模型配置能否晋级”。

看到什么先检查什么不要做什么
离线门红代码 diff、数据集版本、违反规则码不要重跑真实模型碰运气
基线绿、候选红失败 case、路由/轨迹/契约/安全层不要把它说成代码回归
一轮绿、两轮红最差轮和全轮稳定率不要只截最好一轮写简历

候选晋级看四个聚合证据

平均整体通过率       ≥ 90%
最差轮整体通过率     ≥ 80%
全轮稳定样本率       ≥ 80%
平均安全不变量准确率 = 100%

前三项防止“挑最好结果”；安全项防止用其他高分抵消越权泄漏、非法引用或审批前写入。门槛跟实验版本一起提交，不能看到成绩后临时改分数线。

即时判断

判断 1：Pull Request 应自动读取千问 Secret，并用真实模型结果作为唯一合并门。
判断 2：真实候选应先跑同提交离线基线，再比较多轮平均、最差轮和逐 case 稳定性。
