SERVICEOPS AGENT · LESSON 27

Outbox不是第二份订单，而是可靠通知待办

它记录的核心语义是：“这笔业务已经提交，还有一个完成事实必须送到下游。”

餐厅类比

订单表是厨房真正要做的菜；Outbox是和订单同时放进出餐口的通知小票。小票不是第二份订单，它告诉服务员：“这桌菜已经做好，请可靠通知顾客。”即使服务员临时离岗，小票仍在，回来还能继续处理。

业务事实

return_requests回答：退货申请是否真实存在、属于谁、哪个订单、什么状态。

投递义务

return_outbox_events回答：这笔已提交事实是否已经可靠送入审计链。

没有Outbox会出现什么

执行顺序崩溃结果
先提交业务，再通知审计中间崩溃：退货已存在，但审计永远不知道。
先通知审计，再提交业务业务回滚：审计却记录了一笔实际不存在的退货。

Outbox怎样把窗口关掉

BEGIN PostgreSQL transaction
├─ INSERT return_requests（业务事实）
├─ INSERT return_outbox_events（待投递凭证）
└─ COMMIT / 任一失败则一起 ROLLBACK

事务外：扫描 pending → 投递审计 → 标记 processed
“为什么不和业务事实放在一起？”——其实已经放在一起了

物理提交上：同一个PostgreSQL、同一个连接、同一个事务，保证共同成功或共同回滚。
逻辑模型上：分成两张表，因为退货记录的生命周期是业务状态，Outbox的生命周期是pending、重试、processed、dead-letter。投递失败不应该修改或污染真实退货状态。

为什么单独一张表更合适

原因解释
职责不同业务表是事实来源；Outbox是可靠投递队列。
状态不同业务是submitted；投递是pending/processed/dead-letter。
数量不同一笔业务未来可能产生created、approved、cancelled等多条事件。
扫描不同协调器只需索引和扫描到期pending，不必反复扫描业务表。
数据最小化Outbox只保存下游需要的最小载荷与摘要，不复制完整业务正文。
能不能直接在return_requests加一个published字段？

极简的一种业务、一个事件、一个下游场景可以，这相当于把“专用Outbox”塞进业务表。但出现多事件、多下游、重试、死信和保留策略后，业务表会迅速混入大量投递字段；独立Outbox更通用。

一分钟检验

如果Outbox投递失败，应该回滚已经提交的退货申请吗？

查看答案

不应该。业务事务已经完成，Outbox保留pending并重试。强行回滚或删除业务事实会把“通知失败”错误变成“业务事实被撤销”。
