ServiceOps Agent · 第 17 步配套课

一家店开两个窗口，为什么不会各记各的账？

这一课不要求你先懂运维。只用“取号台、业务窗口、总账本、装修队”四个比喻，理解Nginx、双Agent、PostgreSQL和Alembic。

一句话结论：Nginx负责把客人分给两个窗口；两只Agent只处理业务、不私藏进度；PostgreSQL保存共同事实；Alembic在营业前统一升级表结构。

现在 Docker 里不是两个，而是五个角色

你访问 localhost:8000
          │
          ▼
    gateway / Nginx（取号台）
          │轮流分配
       ┌──┴──┐
       ▼     ▼
   agent-a  agent-b（两个业务窗口）
       └──┬──┘
          ▼
     postgres（共同总账本）

   migrate（营业前装修队，做完就退出）

四个词怎么记

负载均衡

取号台不让所有客人都挤到一个窗口。当前默认轮流分：A、B、A、B。

无状态实例

窗口员工不把关键资料锁进个人抽屉。换一个员工，也能从共同总账本继续办理。

Schema Migration

数据库“装修图纸”有版本。营业员不能边接客边擅自加柜台，装修队先统一施工。

怎么证明不是嘴上说“多实例”

  1. 先让Nginx连续请求，确实观察到A和B。
  2. 停掉B，只让A创建一条等待审批的退货线程。
  3. 启动B，再停掉A。
  4. 把同一个thread_id交给B审批。
  5. B成功生成退货编号并读到有效审计链。
  6. 最后自动恢复A和B。
uv run python examples/17_multi_instance_failover.py

如果状态只在A的内存里，第4步一定找不到原来的暂停位置。它能成功，说明Checkpoint、业务记录和审计事实真的位于共享PostgreSQL。

为什么迁移任务“Exited (0)”反而是成功

容器应该长期运行吗正常状态
gateway / agent-a / agent-b / postgres是healthy
migrate否执行 upgrade head 后 Exited (0)

装修队不需要全年住在银行。退出码0表示施工完成；非0才表示装修失败，两个Agent也会被Compose拦住不启动。

同时点两次“批准”怎么办

不能只相信前端按钮变灰。两个实例可能同时收到重试。项目在数据库里按幂等键加事务锁，再用主键/唯一约束兜底。真实并发测试结果是：一边首次创建，另一边读取同一条记录并标记安全重放，总数只增加1。

面试时怎么说

可直接回答：“我把API改成单容器单worker的无状态实例，Compose启动agent-a和agent-b，Nginx作为唯一回环入口做轮询和Docker DNS重解析。两只实例共享官方Postgres Checkpointer与业务库。业务DDL由Alembic一次性迁移任务管理，API不再启动建表。我做了A创建、B恢复的故障切换演练，也用两个独立连接池并发验证相同幂等键只能创建一条记录。”

诚实边界：本机Compose证明设计与实现，不等于云上生产高可用。生产仍需TLS、Secret、数据库主从/托管高可用、备份恢复、监控告警和容量压测。
