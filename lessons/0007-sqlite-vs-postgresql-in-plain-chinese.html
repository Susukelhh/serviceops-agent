SQLite 是个人抽屉，PostgreSQL 是共享档案室

这一课只解决一个问题：我们已经有 SQLite，为什么下一步还要引入 PostgreSQL？

一句话答案：SQLite适合一份程序在本地管理自己的文件；PostgreSQL适合多份程序通过网络共同使用一套数据。

先用档案柜理解

SQLite：个人抽屉

Agent旁边放着一个数据库文件，程序直接打开、读取和修改。安装简单，适合学习、单机演示和小型工具。

PostgreSQL：共享档案室

数据库是一个独立运行的服务，多个 Agent都向档案管理员发送请求。管理员统一处理读取、写入、权限和同时操作。

当前项目为什么先用 SQLite

目前只有一个 ServiceOps Agent容器，SQLite文件和它放在同一套本地 Docker环境里。这就像只有一名员工使用自己的档案抽屉：便宜、简单、方便调试。

一个 Agent 容器
      ↓ 直接打开文件
checkpoints.sqlite3
serviceops.sqlite3

这不是“落后技术”，而是当前单机阶段合适的选择。SQLite官方也强调，它和 PostgreSQL解决的是不同问题。

多个 Agent容器会遇到什么问题

以后为了接待更多用户，我们可能同时启动多个 Agent容器。如果每个容器都有自己的 SQLite抽屉：

用户第一次请求 → Agent A → A 的 SQLite 有聊天记录
用户第二次请求 → Agent B → B 的 SQLite 没有那条记录

用户会觉得 Agent“失忆”。而且多个程序同时争抢同一个网络文件，也不是 SQLite最适合的使用方式。

换成 PostgreSQL 后

Agent A ─┐
Agent B ─┼── 通过网络请求 ──→ PostgreSQL 共享档案室
Agent C ─┘                       保存统一状态

无论用户的请求落到 A、B 还是 C，它们都能访问同一套聊天状态、退货记录和审批记录。这就是“共享状态”。

形态应用直接读写本地文件独立数据库服务接受连接

不要得到错误结论：PostgreSQL不是永远优于 SQLite。个人记事本不需要建设公司档案中心；但当多个 Agent实例需要共享数据时，公司档案室式的数据库更合适。

和 LangGraph有什么关系

LangGraph的 Checkpointer可以理解为“对话进度存档员”。用户说到一半、等待人工审批或服务重启时，它负责保存图执行到了哪里。项目现在已使用官方 PostgreSQL Saver，让多个 Agent容器能够读取同一份进度；SQLite仍保留给不启动 Docker 的单机学习。

面试表达：项目早期使用 SQLite降低本地开发复杂度；容器化验证后，为支持多实例共享 Checkpoint和业务状态，已经迁移到 PostgreSQL。迁移目的不是堆技术名词，而是解决多实例状态共享和并发访问问题；SQLite仍作为本地回退模式。
小测验：三份 Agent容器需要共同读取同一用户的对话进度，更像需要哪一种存储？
