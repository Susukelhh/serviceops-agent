SERVICEOPS AGENT · LESSON 26

批准不是直接写库：中间还有三道可靠性边界

目标：能用一笔退货申请解释 interrupt、幂等键、事务 Outbox 和可校验哈希链各自解决什么问题。

生活类比：银行转账授权

客户先填单，柜员冻结待办内容，主管签字后系统才记账。记账与“待通知回执”放进同一个保险柜；通知员稍后把完成事实送到审计档案室。流水号防止重复记账，档案页互相引用摘要，方便发现历史被改过。

1. 冻结草案

提取订单与原因，校验本人已签收订单；尚未写业务表。

2. interrupt

Checkpoint保存 State 与暂停位置，只暴露最小审批负载。

3. 决定先落审计

reviewer身份来自JWT；先追加decision，再用Command.resume恢复。

4. 二次复查

草案、严格布尔批准、可信身份和订单资格全部重新校验。

5. 原子提交

同一事务写return_requests和pending Outbox；任一失败全部回滚。

6. 至少一次投递

协调器把pending变成workflow_completed审计事件。

7. 幂等确认

重复投递返回原审计事件；下游确认后Outbox才标processed。

8. 全链重算

auditor重新检查位置、前驱和每条SHA-256，而非相信数据库结论。

三个稳定标识，不可混用

标识解决的问题生成依据
thread_id恢复哪一条工作流首次聊天时服务端UUID
idempotency_key同一业务效果是否已发生客户端稳定复用；缺省仅用本次request_id
outbox event_id同一线程完成事件是否已投递UUID5(thread_id + 固定事件类型)

同键如何判断重放还是冲突

existing.idempotency_key == incoming.key
AND existing.user_id == incoming.user_id
AND existing.order_id == incoming.order_id
AND existing.reason == incoming.reason
→ 安全重放，返回同一个 RR 编号

同键但任一业务字段不同 → idempotency_conflict，禁止覆盖

四类数据职责

边界回答的问题关键内容
Checkpoint流程做到哪里？草案、interrupt、审批决定、下一节点
业务记录现实中发生了什么？RR编号、用户、订单、原因、submitted、幂等键
Outbox哪个完成事实还没可靠送出？最小审批元数据摘要、RR编号、pending/processed/dead_letter
审计链谁授权、最终结果是什么、历史是否被普通修改？decision/terminal事件、主体、摘要、位置、前驱哈希

哈希链定义

proposal_digest = SHA256(canonical_json(完整强类型草案))
comment_digest = SHA256(审批备注规范化文本)
first.previous_event_hash = "0" × 64
event_hash = SHA256(canonical_json(事件全部字段 - event_hash))
next.previous_event_hash = current.event_hash
诚实边界

这里实现的是应用级只追加与可检测篡改。它能发现字段修改、链中删除和错误前驱；不能阻止数据库管理员重写整库并重算全部哈希，也无法单独证明链尾未被删除。SHA-256摘要不是加密或数字签名。生产级不可抵赖还需要外部锚点、WORM存储、KMS/HSM数字签名和权限隔离。

为什么决定要在业务执行前写审计？

如果服务在授权与执行之间崩溃，审计员仍能看到“有决定、无终态”的异常流程；否则可能完全丢失谁授权过的证据。

为什么业务记录和completed审计不直接双写？

两个持久化动作之间可能崩溃。Outbox让业务记录与待投递事实在一个本地事务提交，再用至少一次投递和幂等消费者补齐审计。

为什么不叫exactly-once？

审计append成功而Outbox尚未标记时仍可能崩溃，重启后只能再次投递。准确说法是：传输至少一次，消费者幂等，获得业务效果上的一次。

一分钟检验

场景：审计completed已经追加成功，服务在Outbox标记processed前崩溃。重启后应该跳过还是重投？

查看答案

必须重投。审计仓库用稳定事件ID和完整语义识别为幂等重放，然后协调器再把Outbox标为processed；不会生成第三条审计事件。

速查：退货写流程安全卡 · 实验记录：事务Outbox、审批哈希链。

一手资料：LangGraph Interrupts · AWS Transactional Outbox · OWASP Logging。哪里不清楚，拿一个崩溃时点问我，我们逐行判断哪张表应该出现什么。

面试一句话：thread_id负责恢复流程，幂等键负责业务效果至多一次，Outbox负责跨边界最终投递，哈希链负责让审批历史的普通篡改可被检测。
