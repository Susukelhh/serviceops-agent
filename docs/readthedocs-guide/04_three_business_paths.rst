====================================================================================================
4. 三条业务路径怎么走
====================================================================================================

FAQ：先找证据再回答
====================================================================================================

示例问题：“电子商品激活后还能退吗？”

.. code-block:: text

   意图分类 → 业务范围门 → Qdrant / BM25 独立召回 → RRF 融合
            → 证据充分性判断 → 引用校验 → 回答 / 转人工

关键规则：

* 天气、投资、医疗、索取内部规则等高置信域外问题，在做 Embedding 前就拒绝。
* 检索只使用处于发布状态且对外公开的知识，草稿和退役政策不进入索引。
* Qdrant 与 BM25 都从完整的已发布公共切片中检索；RRF 只按两路名次融合，不生成新知识。
* 每条候选保留两路原分数和名次，页面能解释它是单路命中还是双路共同命中。
* “主题相似”不代表“足以回答”。回答器必须明确给出 ``is_answerable`` 和候选范围内的引用。
* 证据不足、生成异常或引用越界统一转人工。

订单：受约束的小循环
====================================================================================================

示例问题：“查一下订单 S0100001 到哪了。”

.. code-block:: text

   初始化 → 规划 → 只读工具 → 观察 → 再规划 → 汇总

它像一个有护栏的 ReAct 循环，但页面不会展示模型隐藏的思考文字，只展示工程动作：计划了哪个工具、参数是否通过、工具是否成功、下一步去了哪里。

安全点在于：模型提供的订单号只是候选参数，真正的用户身份来自 JWT；仓储层按 ``user_id + order_id`` 查询，不能跨用户读取。

退货：先暂停，再由人决定
====================================================================================================

示例问题：“我要退订单 S0100001，原因是买错了。”

.. code-block:: text

   生成退货草案
        ↓
   interrupt 暂停 ──保存 Checkpoint──► 等待 reviewer
        │                                  │
        └──────── Command(resume=决定) ◄───┘
                           │
                      批准 / 拒绝
                       │       │
                 写业务库     零写入结束
                       │
                 同事务写 Outbox

为什么一定要暂停：创建退货记录会改变业务数据。如果只让模型在聊天里说“已经为你退货”，就可能出现口头承诺和数据库事实不一致。

批准后的真实写入包含：

* 幂等键，避免用户或网络重试造成重复退货；
* 业务记录与 Outbox 同一事务提交；
* 审批决定写入可校验哈希链；
* Outbox 发送失败时可由对账任务重试。

人工路径：不是失败垃圾桶
====================================================================================================

系统在以下情况主动转人工：

* 意图低置信或不在支持范围；
* RAG 没有足够证据；
* 模型输出结构损坏；
* 工具调用越权、重复、超步数或失败；
* 审批状态和恢复数据互相矛盾。

“转人工”是安全产品设计，而不是程序崩溃。企业系统更关心“错误时是否可控”，而不是所有请求都强行自动回答。
