====================================================================================================
14. 技术栈不是装饰：每个选择解决什么
====================================================================================================

核心选型表
====================================================================================================

.. list-table::
   :header-rows: 1
   :widths: 22 33 45

   * - 技术
     - 遇到的问题
     - 为什么这样选
   * - Python 3.12
     - Agent 和模型生态需要快速组合
     - 类型注解成熟，LangChain/LangGraph/FastAPI 生态直接
   * - FastAPI
     - 需要 HTTP API、Swagger 和异步生命周期
     - 和 Pydantic 配合紧密，适合 Python 服务
   * - Pydantic v2
     - 用户、模型和工具输入都可能格式异常
     - 在边界处把随意数据变成可验证结构
   * - LangGraph
     - FAQ、订单、退货路线不同，还要循环、暂停、恢复
     - 状态、节点、条件边和 Checkpoint 都能显式表达
   * - LangChain
     - 需要兼容模型调用与 Tool Schema
     - 只用在适合的适配层，不让框架接管业务安全
   * - 通义千问兼容 API
     - 需要真实分类、规划、Embedding 和 Grounded 回答候选
     - 国内可用，并通过 OpenAI 兼容接口降低供应商耦合
   * - 独立 Qdrant
     - 双 Agent 不能各自保存随进程消失的向量索引
     - Compose 独立服务、具名卷持久化、Collection 就绪探测
   * - BM25 + RRF
     - 语义召回可能漏掉精确术语，两个分数单位又不能直接相加
     - 两路各查全库，用倒数名次融合，结果保留通道解释
   * - SQLite
     - 初学和单机恢复需要零额外服务
     - 一个文件即可运行，适合教学
   * - PostgreSQL
     - 双 Agent 需要共享流程和业务数据
     - 支持事务、连接池、约束、迁移和可靠备份工具
   * - Alembic
     - 表结构需要随版本升级
     - 让数据库变化可记录、可重复执行
   * - JWT + RBAC
     - 用户、审批人、审计员和开发者权限不同
     - 以签名身份和最小 Scope 隔离职责
   * - OpenTelemetry
     - Agent 链路长，失败位置难定位
     - 用统一 Trace 关联 API、节点、工具和数据库动作
   * - Docker Compose
     - 不同电脑环境不一致，多个服务难手工启动
     - 一份配置启动网关、双 Agent、迁移、数据库与 Qdrant
   * - Nginx
     - 需要统一入口、分发双实例和基础限速
     - 成熟、轻量，适合本地模拟企业入口层
   * - Pytest/Ruff/Mypy
     - Agent 不能靠手工点几次判断质量
     - 分别验证行为、常见代码问题和类型边界
   * - GitHub Actions
     - 本机通过不代表干净环境通过
     - 每次提交自动在 Linux 重跑离线质量门

为什么没有“一个最强模型解决全部”
====================================================================================================

模型有随机性、费用和外部故障，企业规则却需要稳定、可审计。项目把职责拆开：

* 模型擅长理解自然语言、语义匹配和组织答案；
* 规则擅长明确安全边界和高置信域外判断；
* Schema 擅长验证格式；
* 数据库擅长保存事实和事务；
* 人工审批负责高风险业务决定。

这是“让合适的组件做合适的事”，不是否定模型能力。

为什么默认离线、候选才用真模型
====================================================================================================

开发和 CI 每次都调用真模型会受网络、费用、限流和输出波动影响。确定性 Profile 用来验证工程逻辑；真实 Profile 用开发集选型，
冻结后再用锁定集验收。两套配置各自解决不同问题。

RAG 和微调不是二选一
====================================================================================================

RAG 适合频繁变化、需要引用来源的企业事实；微调更适合稳定的行为模式、格式、语气或领域表达。

本项目的问题是“售后政策从哪里来、能否证明答案”，所以优先 RAG。即使以后用 LoRA 微调模型的工具选择或回答风格，
政策事实仍应通过 RAG 获取。当前项目没有微调实验，面试时不能把“了解 LoRA”写成项目能力。
