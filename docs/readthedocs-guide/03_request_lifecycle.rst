====================================================================================================
3. 一次用户请求的一生
====================================================================================================

下面从用户输入“帮我查订单 S0100001”开始，顺着真实代码走完整条链路。

第 1 步：请求来到统一入口
====================================================================================================

浏览器调用 ``POST /api/v1/chat``。FastAPI 先把 JSON 转成 ``ChatRequest``，Pydantic 检查字段类型和长度。
这一步像窗口工作人员先检查表格有没有乱填，格式不合法就不会进入后面的 Agent。

第 2 步：检查身份和容量
====================================================================================================

JWT 校验签名、签发方、使用对象、过期时间、角色和权限。后端从 Token 中取得可信 ``user_id``，
而不是相信用户在问题里写的“我是张三”。随后容量保护器尝试取得一个有限“工位”；工位满时短暂等待，仍无空位就返回 503。

这解决两个问题：

* 防止用户在自然语言里冒充别人查订单；
* 防止高峰期所有请求无限堆积，把数据库和模型一起拖死。

第 3 步：创建 thread_id 和初始 State
====================================================================================================

``thread_id`` 类似业务流水号。同一个需要暂停和恢复的流程必须继续使用同一个编号。
初始 State 包含用户问题、可信身份、请求编号和事件列表，不包含隐藏思维链。

第 4 步：标准化和意图分类
====================================================================================================

``normalize_request`` 清理输入；``classify_intent`` 把请求归为 FAQ、订单状态、退货申请或人工处理。
分类器可以使用零费用确定性版本，也可以使用千问结构化输出版本。低置信度或模型异常会安全转人工。

第 5 步：条件路由选择订单路径
====================================================================================================

``select_response_path`` 只返回有限的路线键。订单意图进入：

.. code-block:: text

   initialize_order_agent
        ↓
   plan_order_action
        ↓
   execute_order_tool
        ↘
         回到 plan_order_action
        ↓
   finalize_order_response

路由函数采用“默认转人工”的原则：只允许明确合法的状态继续自动处理。

第 6 步：规划器提出受约束动作
====================================================================================================

规划器只能从四种动作中选择：调用工具、完成回复、追问参数、转人工。即使使用真实模型，输出也必须通过 Pydantic Schema。
它不能直接执行 SQL，也不能自己新增一个工具名。

第 7 步：后端再次验证并执行工具
====================================================================================================

工具执行节点会检查：

* 工具名是否在白名单；
* 参数是否符合 Schema；
* 订单号是否重复调用；
* 工具步数是否超限；
* 查询使用的 ``user_id`` 是否来自认证上下文。

通过后才调用 ``get_order_status``。工具返回的是结构化结果，不是任意长文本。

第 8 步：观察结果并结束循环
====================================================================================================

工具结果写回 ``tool_execution_records``。规划器再次读取 State，正常情况下选择 ``finish``；
最终节点重新校验执行记录，并生成确定性订单答复。循环有最大工具步数，因此不会无限转圈。

第 9 步：保存快照与观测信息
====================================================================================================

LangGraph Checkpointer 在节点边界保存 StateSnapshot。OpenTelemetry 同时记录请求、节点、工具和结果类型等低敏信息。
控制台可以按时间顺序读取脱敏快照，展示“哪个节点刚执行、哪些公开字段发生变化”。

第 10 步：返回 API 响应
====================================================================================================

API 返回答案、意图、工具名、公开事件、引用或审批状态。响应不包含模型隐藏推理原文、Token、数据库密码或内部异常堆栈。

你应该记住的核心
====================================================================================================

.. tip::

   模型负责“在允许范围内建议下一步”；路由器和执行器负责“判断是否合法并真正执行”；Checkpoint 负责“让流程可恢复”；审计与 Trace 负责“让结果可追查”。
