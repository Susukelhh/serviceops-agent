====================================================================================================
10. 稳定性与观测：出问题时要看得见
====================================================================================================

模型调用为什么不稳定
====================================================================================================

外部模型可能超时、限流、鉴权失败、返回 5xx，或者虽然 HTTP 成功却没有按 Schema 输出。
项目把这些错误分成可重试和不可重试类型，并设置单次超时与最大重试次数。

重试不是越多越好。假设外部服务已经拥堵，每个请求重试三次会把一份压力放大成四份。因此默认最大重试 2 次，
业务层仍保留安全转人工或确定性降级。

确定性后端的意义
====================================================================================================

本地和 CI 默认使用 Mock 分类器、确定性规划器、Hash Embedding 和抽取式回答。它们不是为了冒充真实模型效果，
而是让工程回归不受网络、费用和模型随机性影响。

真实千问候选通过独立脚本、明确付费确认、冻结配置和锁定集验收。这样“代码是否稳定”和“模型是否够好”不会混成一个分数。

容量与过载保护
====================================================================================================

* API 实例使用有限信号量保护高成本接口。
* PostgreSQL 连接池设置最小和最大连接数。
* Nginx 对入口做限速和连接管理。
* 工具循环有最大步数和重复调用检测。
* Docker 对 CPU、内存和进程数设置边界。

这些措施的共同目标是：局部异常时快速失败或降级，不让问题无限扩散。

OpenTelemetry 是什么
====================================================================================================

OpenTelemetry 像统一的快递单号。一次请求经过 API、图节点、检索、工具和审批时，各段记录关联的 Trace 和 Span。
它回答“慢在哪里、失败在哪里”，不是保存用户完整问题或模型隐藏推理。

项目记录的内容包括：

* 低基数意图、结果类型和节点名称；
* 请求耗时、容量拒绝、工具与审批结果指标；
* Trace ID 和 Span ID；
* 经过截断与清洗的结构化日志。

项目不会把 API Key、JWT、数据库密码或完整异常敏感内容写入 Trace 属性。

健康检查和故障切换
====================================================================================================

Nginx 后面有 agent-a 和 agent-b。两只实例使用同一镜像和 PostgreSQL。请求可以落到任意实例；因为 Checkpoint 在共享数据库，
agent-b 可以继续 agent-a 暂停的流程。这证明了共享状态，不等同自动跨地域容灾。
