====================================================================================================
7. RAG：先查企业资料，再组织答案
====================================================================================================

RAG 解决什么问题
====================================================================================================

大模型可能不知道企业最新政策，也可能把“听起来合理”的内容当成事实。RAG 的做法是先检索企业允许公开的知识，再要求回答器只依据这些材料作答。

项目的完整路线
====================================================================================================

.. code-block:: text

   原始文档
      ↓ 发布状态过滤
   Chunk 切片（500 字符，重叠 80）
      ↓
   Embedding 转成向量
      ↓
   ┌─ Qdrant 从完整 Collection 取向量 Top-8 ─┐
   │                                           │
   └─ BM25 从全部知识切片取关键词 Top-8 ───────┘
                         ↓
                 RRF 合并两张排名榜
                         ↓
   取 Top-3 作为证据
      ↓
   判断证据是否真的能回答
      ↓
   生成答案并校验引用 / 转人工

为什么要切片
====================================================================================================

整份政策直接放进模型会又长又吵。切片像把一本手册拆成带编号的小卡片，查询时只拿最相关的几张。

当前使用字符窗口 500、Overlap 80。80 个重叠字符用于保留跨边界句子的上下文。这个参数来自当前小型语料的基线，不是所有企业文档的通用最佳值。
真实文档扩大后，应对不同 ``chunk_size``、``overlap``、标题感知切片和父子文档策略做对照实验。

Embedding 是什么
====================================================================================================

Embedding 把文本变成一串数字，让语义接近的文本在数字空间里更靠近。

项目提供两种后端：

* **Hash 1024 维**：完全离线、便宜、结果稳定，适合测试，但理解同义表达的能力弱。
* **qwen3.7-text-embedding 1024 维**：真实语义候选，能改善低词面重合问题，但需要 API 费用和网络。

第 27 步实验中，千问候选在语义正例上明显好于 Hash，但锁定集出现 50% 负例误召回，因此没有仅凭检索分数直接晋级。
这次失败促成了下一层“证据充分性判断”。

Qdrant 做什么
====================================================================================================

Qdrant 像按语义距离找资料的索引柜。本机直接运行和自动测试仍可使用内存模式；Docker Compose 则启动独立
``qdrant`` 服务，并把数据写入 ``serviceops-qdrant`` 具名卷。两只 Agent 通过 ``http://qdrant:6333`` 共享同一 Collection。

这解决了两个问题：Agent 重启不会让向量索引跟着进程消失；agent-a 与 agent-b 不会各自维护互不相干的知识副本。
``/ready`` 还会读取活动 Collection，Qdrant 断线时 Agent 返回未就绪，网关不应继续把它当成可用服务。

业务范围门为什么在 Embedding 前
====================================================================================================

天气或股票问题即使包含“退款”等词，也不属于售后知识问答。范围门先拒绝高置信域外请求，可以减少误召回，也省下一次 Embedding 调用。

实验发现只提高相似度阈值虽然能把 FPR 降到 0，却让 Recall@5 从 100% 跌到 20.8%。
加入范围门后，开发集 FPR 从 100% 降到 0，正例 Recall 保持 100%。这说明“是否属于业务范围”和“文档是否相似”是两个不同问题。

BM25 与 RRF 做什么
====================================================================================================

向量检索擅长同义表达，BM25 更看重发票术语、政策名和精确关键词。旧版 BM25 只检查向量 Top-5；新版
``BM25CorpusRetriever`` 在启动时为全部治理后切片建立词频索引，每次查询独立给出自己的 Top-8。

RRF 不直接比较“余弦 0.8”和“BM25 3.2”这两种不同单位，而只看各自在本榜的名次：

.. code-block:: text

   某切片的 RRF 分数
     = 1.0 / (60 + 向量名次)
     + 0.8 / (60 + BM25 名次)

两路共同命中的切片通常更靠前；只被某一路发现的切片仍有机会进入最终候选。最终结果同时保留
``dense_score``、``lexical_score``、两路名次和 ``fusion_method=rrf``，调试页面可以解释排序来源。

旧的 ``off`` 纯向量模式和 ``bm25`` 候选内重排模式仍保留，用于复现第 26～29 步历史实验；生产 Compose 显式选择
``hybrid_rrf``，不会把历史基线和新链路混成一组指标。

旧版实验曾证明：候选内 BM25 让开发集 Top-1 从 80% 提升到 95%，锁定集从 90% 提升到 100%。
这些数字不能直接归功于新版 RRF。

第31步随后建立了四路同变量对照。74条开发题中，冻结RRF把Top-1从纯向量83.87%提升到93.55%，
比旧候选内重排91.94%再提高1.61个百分点。但纯向量Recall@5原本就是100%，关键词救回数为0，
所以这次只能证明排序改善，不能宣称召回率提升。

冻结参数在16条新锁定题中保持12条知识内题Recall@5为100%、Top-1为91.67%，却误放行2/4条域外问题，
FPR为50%，最终Gate FAIL。失败说明RRF负责排资料，不负责判断用户问题是否属于业务范围；开发优胜的
关键词权重1.50没有晋级生产，当前配置保持不变。

证据充分性与幻觉控制
====================================================================================================

“找到相似文档”不等于“文档包含答案”。真实回答器必须返回结构化的 ``is_answerable``，并且引用只能来自本次候选白名单。
第 29 步端到端锁定集中，候选链路把无依据回答率从基线的 50% 降到 0%；但它只有 12 条受控题，不能宣传为线上幻觉率永久为 0。
