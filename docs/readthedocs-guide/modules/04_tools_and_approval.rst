====================================================================================================
8. 工具与审批：模型不能直接碰业务库
====================================================================================================

工具是什么
====================================================================================================

工具是后端预先写好的函数。模型只能选择是否调用，并填写受限制的参数；真正执行、鉴权和错误处理仍由普通 Python 代码负责。

项目有两个核心工具：

* ``get_order_status``：只读，查询当前用户自己的订单状态。
* ``create_return_request``：写入，创建退货申请，必须经过人工审批。

为什么使用 LangChain Tool
====================================================================================================

LangChain 在这里主要提供统一的工具描述和 Schema 接口，使真实模型能用 Tool Calling 形式提出动作。
整个工作流并不是由 LangChain Agent 自动生成，而是由 LangGraph 显式编排。

四层保护
====================================================================================================

.. list-table::
   :header-rows: 1
   :widths: 20 35 45

   * - 层
     - 检查内容
     - 防止的问题
   * - 规划 Schema
     - 动作、工具名、参数类型是否有效
     - 模型输出随意文本或不存在的动作
   * - 执行白名单
     - 工具名是否明确允许
     - Prompt 注入诱导调用未知工具
   * - 可信身份绑定
     - user_id 是否来自 JWT 上下文
     - 用户自然语言冒充他人
   * - 业务仓储
     - 订单归属、退货资格、幂等键
     - 越权查询、重复写入、无资格退货

Human-in-the-loop 如何工作
====================================================================================================

退货草案准备好后，``interrupt`` 把最小审批信息交给 API，并暂停当前图。Checkpointer 保存流程位置。
审批人通过独立接口提交批准或拒绝，API 使用 ``Command(resume=...)`` 恢复原 ``thread_id``。

重要的是：暂停之前没有创建退货业务记录。批准后才允许进入唯一写工具节点；拒绝则以零业务写入结束。

幂等是什么
====================================================================================================

幂等意味着同一个有效请求重复执行，不会产生多份退货单。网络超时后客户端可能重试，审批接口也可能被重复点击，
所以系统使用稳定的幂等键和冲突检查区分“同一次重试”和“不同内容误用了同一编号”。

为什么没有使用 MCP
====================================================================================================

MCP 主要解决“用统一协议连接外部工具和资源”的问题。本项目只有少量内部工具，重点是权限、审批、幂等和审计，直接 Tool Calling 更容易控制和讲清边界。

未来当工具来自多个团队、不同进程，或需要复用第三方 MCP Server 时，可以增加 MCP Client 适配层；但 MCP 不会自动解决业务授权和高风险审批，它只是连接协议。
