# 第五步：受约束生成、引用白名单与 RAG 离线评测

## 本步目标

第四步解决“能否找到允许使用的企业证据”，第五步继续解决两个问题：

1. 如何让真实大模型把证据整理成简洁答案，但不能依赖模型记忆猜测；
2. 如何用固定数据和指标证明检索质量，而不是只展示一条成功 Demo。

最终 FAQ 链路是：

```text
意图分类
→ Qdrant Top-K 检索
→ 证据阈值门
→ 摘录式或 LLM 受约束生成
→ 候选 chunk_id 引用白名单
→ 最终答案完整性门
→ 成功返回或安全转人工
```

## 三道安全门分别负责什么

第一道门位于意图分类之后。未知意图、低置信度或分类模型故障不会进入自动业务路径。

第二道门位于 FAQ 检索之后。只有 `has_sufficient_evidence=True` 且存在经过阈值过滤的
`RetrievalHit`，才能调用回答器。Embedding、Qdrant 故障或无命中都直接转人工。

第三道门位于回答生成之后。它要求：

- `faq_answer_grounded` 必须显式为 `True`；
- 最终答案非空；
- 至少存在一条引用；
- 每个引用 ID 都来自本次实际检索候选集合。

任何字段缺失都采用人工安全默认路径。模型即使自称 `is_answerable=true`，也不能绕过确定性
白名单。这种设计把“概率模型负责语言组织”和“代码负责权限与不变量”明确分开。

## 为什么不让模型直接输出完整 Citation

模型只返回：

```text
answer
citation_ids
is_answerable
```

其中 `citation_ids` 只能选择提示中提供的 `chunk_id`。最终 `Citation` 的标题、来源、版本和
生效日期由服务端根据白名单 `RetrievalHit` 重新构造，而不是相信模型填写。这样可以避免：

- 模型编造不存在的来源；
- 模型篡改制度版本或生效日期；
- 模型把未授权文档写成引用；
- API 返回的引用和实际证据不一致。

集成测试中的 `FabricatedCitationAnswerClient` 会故意返回 `fabricated-chunk-id`。整张图必须清空
草稿和引用，记录 `generation_invalid_citation`，再由人工节点生成安全文案。

## 两种生成实现

### 1. 默认 `extractive`

它直接组织前两条审核证据，不访问大模型。优点是零费用、完全可重复、每段内容能直接追溯，
适合 CI、面试现场和检索问题排查。

### 2. 可选 `llm`

它使用 LangChain `with_structured_output` 和 Pydantic `GroundedAnswerDraft` 调用千问兼容接口。
系统提示明确规定证据是唯一事实来源，问题与 evidence JSON 都按不可信数据处理，并限制证据
总字符数。认证、限流、超时、连接和结构化响应错误都会归一化成有限故障码，再转人工。

在 `.env` 中切换：

```dotenv
SERVICEOPS_LLM_BACKEND=openai_compatible
SERVICEOPS_RAG_GENERATION_BACKEND=llm
SERVICEOPS_RAG_MAX_CONTEXT_CHARS=4000
```

2026-08-20 已使用本机配置的 `qwen-plus` 完成一次真实链路验证：发票税号问题经过真实模型分类、
本地检索和真实结构化生成，最终只返回 `KB-INVOICE-001` 的合法候选引用。验证过程没有打印或
写入 API Key。

## 评测集为什么必须同时有正例和负例

只使用知识库内问题会鼓励把阈值调得很低：Recall 可能提高，但天气、写诗或内部制度问题也会
误召回。当前数据集包含：

- 8 条正例：发票、七天退货、保修、人工客服；
- 3 条负例：天气、写诗、未发布内部补偿制度。

负例既检查相关度阈值，也验证治理过滤后的内部文档不会以“知识答案”形式出现。

## 当前四个指标

- `Recall@K`：正例中，Top-K 至少出现一个期望文档的比例；
- `MRR@K`：每个正例首个相关文档排名倒数的平均值，第一名得 1，第二名得 0.5；
- 检索决策准确率：正例正确召回加负例正确拒绝，占全部样本的比例；
- 负例误召回率：负例中仍返回任意证据的比例，越低越好。

当前 1024 维 Hash Embedding、K=3、阈值 0.10 的离线结果是：

| 指标 | 结果 |
|---|---:|
| Recall@3 | 1.000 |
| MRR@3 | 1.000 |
| 检索决策准确率 | 1.000 |
| 负例误召回率 | 0.000 |

这只证明当前 11 条小型回归集通过，不能宣称真实生产问题达到满分。后续应持续加入同义改写、
错别字、长问题、多意图、相邻制度干扰和线上失败样本，并分别校准 Hash 与真实 Embedding 阈值。

## 本步测试

- 第三道纯路由门对缺标记、空答案和空引用默认转人工；
- 模型伪造引用 ID 时草稿被丢弃，危险正文不进入最终响应；
- `.env` 即使启用真实千问，pytest 仍强制使用离线后端；
- 11 条标准检索样本持续通过当前 Hash 基线质量门；
- 从项目外工作目录运行第四、第五步示例仍能找到知识和评测数据；
- 原有订单越权保护、模型故障、API 和 RAG 测试全部不回归。

## 面试追问与回答方向

- 为什么结构化输出不能替代服务端白名单校验？
  结构化输出约束形状，不保证字段事实正确，权限和引用集合仍须由代码验证。
- 为什么 MRR 高不代表答案一定正确？
  MRR 只评估首个相关来源排名，不评估切片内容是否足够，也不评估生成忠实度。
- 阈值如何选择？
  在代表性正负例上比较 Recall、误召回、人工成本与错误回答成本，并按 Embedding 模型分别校准。
- 为什么保留 extractive 基线？
  它把检索和生成质量解耦，支持零费用回归，也能量化真实生成带来的收益与风险。
- 如何评估生成答案？
  后续增加引用正确率、答案忠实度、关键信息覆盖、拒答准确率，并保留人工抽检集。
