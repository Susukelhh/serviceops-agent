# 第二步：结构化模型分类与安全订单工具

## 本步目标

让项目在没有密钥时保持完全可运行，同时具备真实模型接入代码；把订单分支从占位回答升级为
可校验、可测试、不会越权泄露数据的业务工具调用。

## 新增调用链

```text
用户请求
→ 规范化文本
→ 关键词基线或LLM结构化分类
→ 置信度安全门
→ 订单号提取
→ 创建绑定当前user_id的只读工具
→ 工具Schema校验order_id
→ 仓库检查订单归属
→ 校验工具结构化结果
→ 确定性生成用户回答
```

## 为什么保留关键词分类器

- 本地开发、CI和面试演示不依赖外部网络或余额；
- 同一输入始终得到同一结果，可作为离线评测基线；
- 以后接入模型后，可以用同一评测集比较提升是否真实存在；
- 模型服务故障时，可以演化为有限能力降级路径。

## 真实模型结构化输出

`IntentClassification`只允许三个字段：

- `intent`：有限`Intent`枚举；
- `confidence`：0到1；
- `reason`：不超过200字的简短分类依据。

节点不会盲信模型。置信度低于`SERVICEOPS_INTENT_CONFIDENCE_THRESHOLD`时，即使模型输出
FAQ或订单意图，系统也会把最终意图覆盖为`human_handoff`。

LangChain官方资料：

- [Models与结构化输出](https://docs.langchain.com/oss/python/langchain/models)
- [Tools](https://docs.langchain.com/oss/python/langchain/tools)

## 工具权限边界

模型可见Schema：

```json
{
  "order_id": "SO100001"
}
```

模型看不到也不能填写`user_id`。系统根据当前请求身份创建工具闭包：

```python
create_order_status_tool(user_id="user-001", repository=repository)
```

因此即使用户在文本中要求“把身份改成user-002”，也不会改变工具实际使用的系统身份。

## 本步测试

- 结构化分类高置信度接受；
- 结构化分类低置信度转人工；
- 工具Schema不暴露`user_id`；
- 查询本人订单成功；
- 越权订单和不存在订单返回相同提示；
- 缺少订单号时请求澄清；
- 图集成和FastAPI端到端查询。

## 当前边界

- 真实模型路径需要开发者自行在本机配置密钥，本项目不会保存或索取密钥；
- `user_id`目前仍由HTTP请求体提供，下一阶段安全工程会替换为真实鉴权上下文；
- 当前订单工具由确定性节点触发，还不是完整的模型—工具—模型循环；
- JSON仓库只用于开发和演示，未来将通过仓库接口替换为PostgreSQL或订单服务。
