# 第41步：定义多轮会话领域契约

## 这一步解决什么问题

原来的 `/api/v1/chat` 每次请求都会创建新的 LangGraph `thread_id`。这能可靠完成一轮订单查询、FAQ 或退货审批，
但服务端不知道两次请求是否属于同一段用户会话，也没有一份受约束的跨轮记忆。

第41步先不急着把全部聊天记录塞进模型，而是定义三层彼此独立的标识：

1. `conversation_id`：用户可持续使用的一段会话；
2. `turn_id`：会话中的一条用户消息及其处理结果；
3. `workflow_thread_id`：这一轮独立 LangGraph 工作流的 Checkpoint 恢复主键。

这样，一段会话可以包含多轮业务执行，而每轮退货审批仍能独立暂停和恢复，不会把上一轮 Checkpoint 当成下一轮输入继续运行。

## 会话保存什么

`ConversationMemory` 只保存有边界的结构化槽位：

- 当前话题；
- 当前可信订单号；
- 最多10个最近订单号；
- 最近一次意图；
- 最多2000字符的有界摘要；
- 乐观并发使用的记忆版本号。

订单号必须符合 `SO + 6位数字`，最近订单号会规范成大写并去重。历史中的模型回答不被自动提升成真实业务事实；
订单状态、退款结果等仍必须在当前轮重新经过业务工具验证。

## 轮次状态机

每轮只允许单向推进：

```text
accepted -> running -> completed
                    -> waiting_approval -> completed
                    -> failed
```

已完成或失败的轮次不能重新进入运行态。`completed` 必须有用户可见答案，从领域模型层阻止“状态显示完成但结果为空”。

## 哪些历史可以进入模型

`RecentConversationTurn` 是专门面向后续追问解析器的安全投影，只包含：用户消息、助手答案、意图、已验证订单号和引用文档号。
它不包含用户身份、幂等键、审批备注或内部 Checkpoint 对象。

`ConversationContext` 最多接收6轮，并要求轮次序号严格递增。这个限制同时控制上下文长度和并发乱序风险。

## 测试覆盖

单元测试验证了：

- 订单号规范化与去重；
- 非法订单号、额外字段和无时区时间被拒绝；
- 轮次状态只能按允许路径推进；
- 完成状态必须携带答案；
- 模型上下文最多6轮且必须严格有序。
