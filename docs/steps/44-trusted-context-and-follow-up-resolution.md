# 第44步：构建可信上下文并解析多轮追问

## 这一步解决什么问题

第43步已经能保存多轮，但第二轮“它现在到哪了”“那运费呢”仍会被当成独立句子执行。
句子缺少订单号或主题时，分类、检索和工具都无法稳定理解；如果直接把全部聊天记录交给模型，又会带来上下文膨胀、
历史幻觉传播和提示注入风险。

第44步在两者之间增加一层受约束的上下文解析：只取最近有限轮次，只使用明确允许的字段，把当前追问改写成一条
可以独立执行的问题。

## 上下文从哪里来

构建器从会话仓库最多读取50条用于筛选，但最终上下文最多保留最近6条，并且只选择：

- 位于当前轮之前的记录；
- `completed` 或 `waiting_approval` 状态；
- 经过领域Schema校验的安全投影。

`accepted`、`running`、`failed` 和当前轮不会进入上下文，避免并发中的半成品或失败结果污染新请求。

每条安全投影包含原始问题、当时的独立问题、有限意图、已验证订单号和引用文档号。虽然领域投影保留助手答案供后续摘要治理，
本步确定性解析器明确不读取助手答案，因此不会把上一轮模型生成的内容当成新事实。

## 订单指代如何解析

例如第一轮真实执行过：

```text
查询订单 SO100001
```

仓库只在订单工具真正执行后把 `SO100001` 写入 `verified_order_ids`。第二轮用户说：

```text
它现在到哪了？
```

解析结果为：

```text
关于订单 SO100001，它现在到哪了？
```

这里的订单号不能从历史自然语言或助手答案中正则猜取，只能来自：

1. 当前消息明确给出的订单号；
2. 最近一轮工具验证过的订单号；
3. 结构化记忆中的活动订单槽位。

如果当前消息明确写了新订单号，当前选择永远优先，历史不能覆盖它。

## 多订单为什么必须澄清

若上一轮同时查询了 `SO100001` 和 `SO100002`，第二轮问“这个订单什么时候到”，解析器无法证明用户指的是哪一个。
系统不会根据顺序、距离或模型概率猜测，而是构造不含候选订单号的澄清请求，让现有订单Agent返回
`needs_clarification=true`，并且不会执行订单工具。

这体现了多轮稳定性的核心原则：记得更多不是目标，在证据不足时不错误继承才是目标。

## 一般主题追问

“那运费呢”“还有时间限制吗”等问题没有订单指代，但明显延续上一主题。解析器会读取上一轮已经规范化的问题：

```text
延续上一轮问题“退换货政策是什么？”，本轮追问：那运费呢？
```

它不会拼接上一轮助手答案、用户身份、幂等键、审批备注、工具原始结果或完整Checkpoint。
因此后续RAG仍需重新检索当前有效知识，不能因为模型上一轮说过就视为有证据。

## 为什么这一版不用LLM自由改写

指代改写本身也可能产生幻觉。例如模型可能把“它”绑定到较早订单，或生成历史中不存在的订单号。
第44步先实现完全离线、可复现的确定性基线，并把结果原因限制为：

- 当前消息明确引用；
- 唯一已验证订单引用；
- 多订单歧义；
- 上一主题延续；
- 独立新问题。

未来若使用千问做更复杂的语义改写，也必须以这个基线做对照，并在代码层验证模型输出中的每个订单号都属于当前消息或
可信候选白名单。模型不确定、越权引用或结构化输出失败时应回退到澄清，而不是放行猜测。

## 原文与独立问题分开保存

会话详情现在同时返回：

- `user_message`：用户真正输入的原文；
- `standalone_question`：本轮实际交给LangGraph执行的问题。

这样既能审计解析器有没有改错，也能在离线评测集中分别标注“用户追问”和“期望独立问题”。

## 测试覆盖

单元测试验证：

- 当前轮不会进入自己的上下文；
- 超过6轮时只保留最新6轮；
- 当前明确订单号不会被历史覆盖；
- “它”只绑定最近工具验证的唯一订单；
- 多订单指代要求澄清且不把任何候选号送给工具；
- 一般追问继承上一问题主题但绝不复制助手答案；
- 结构化活动订单可以在无历史轮次时提供可信指代；
- 独立新问题不会被旧主题污染。

API端到端测试另外验证了单订单追问真正再次查询正确订单，以及多订单追问不会调用任何订单工具。

## 当前边界与下一步

第44步解决“当前问题到底在问什么”，还没有完整更新跨轮结构化记忆，也没有把会话轮次和审批恢复在同一时刻同步更新。
第45步会把这些上下文结果进一步接入订单、RAG和退货审批生命周期，并维护活动订单、最近意图和可信引用槽位。
