# 第 34 步：端到端有据回答成功率

## 为什么第 29 步之后还要做这一步

第 29 步已经把范围判断、检索、重排、证据充分性判断和引用白名单串了起来。它能回答：

- 正确文档有没有被找到；
- 系统最后选择回答还是拒答；
- 模型返回的引用编号是否属于本轮候选；
- 自动回答是否引用了人工标注的正确父文档。

但它没有直接检查最终答案里的关键事实。例如，系统找到了“七天无理由退货”文档，也返回了合法引用，
却把期限写成“十五天”，旧口径仍可能把这题算作成功。原因是“引用编号合法”只证明引用来自候选，
不能证明答案中的每个结论都被实际引用的切片支持。

第 34 步不再继续堆 Recall、MRR 或更多平均分，而是只把一个更接近用户结果的数字放在最前面：
**端到端有据回答成功率**。

## 唯一主指标

公式为：

```text
端到端有据回答成功率 = 严格完整通过的题数 / 全部密封盲测题数
```

每道题只有 `1` 分或 `0` 分，没有“答对一半”的部分分。

可回答题必须同时满足以下条件才得 `1` 分：

1. 没有被范围门误拒，检索链路确实找到证据；
2. 回答器判断证据充分并给出最终答案；
3. 引用非空，且每个引用都来自本轮检索候选；
4. 人工标注的必要来源都被实际引用；
5. 每个关键事实都在答案中出现；
6. 每个关键事实也能在该事实对应的实际引用切片中找到依据；
7. 答案没有出现人工预先标注的矛盾或禁止结论。

知识缺口题只有在系统拒绝自动回答、同时不返回引用时才得 `1` 分。只要系统拿主题相似的资料硬答，
不论语言多流畅，都记 `0` 分。

因此，范围判断、召回、排序、生成、事实和引用中任意一层出错，整题都是 `0` 分。逐层原因仍会以
有限错误码保留，目的是定位该修哪一层，而不是再包装成第二组主指标。

## 为什么还有“红线失败”

当前契约把以下情况定义为零容忍红线：

- 出现明确的错误或禁止结论；
- 引用非法，或者答案事实无法被实际引用切片支持；
- 对知识库没有答案的问题仍然自动作答。

红线不是第二个平均分。它只是说明：即使总体成功率超过门槛，也不能用许多简单题把一条严重错答平均掉。

## 事实标签怎样工作

私有样本不会要求整段答案逐字一致，而是把答案拆成少量原子事实。每个事实分别保存：

- `answer_all_of`：答案中允许出现的多种等价说法；
- `evidence_all_of`：实际引用切片中必须存在的证据锚点；
- `supporting_document_ids`：哪些父文档可以支撑这个事实；
- `forbidden_claims`：出现任一完整错误说法就失败。

评分前会统一全角半角、大小写、空白和标点，减少模型排版差异造成的机械误判；“七天”和“7天”等
含义相同但字符不同的说法，需要由金标显式列为可接受的替代表述。
这些标签只在模型返回后用于本地评分，绝不会进入问题、检索查询或生成提示词。
揭晓前还会按冻结的切片参数真正切分语料，逐条确认每个证据锚点至少能在允许来源的某个切片中命中，
避免因为人工标签拼错或跨切片而把候选误判为失败。

## 密封盲测纪律

第 34 步的公开配置只保存题量、题集 SHA-256、语料 SHA-256、候选指纹和揭晓前冻结的门槛。
题目正文与事实金标位于 `data/private_evaluation/`，该目录同时被 Git 和 Docker 构建上下文忽略。

当前公开契约声明 25 道新题，其中 19 道可回答题、6 道知识缺口题。它们没有复制第 24～33 步已经揭晓的
问题；加载器还会对问题归一化后检查泄漏。候选的切片、Qdrant、BM25、RRF、Embedding、生成提示和模型
参数都在读取私有正文前形成 SHA-256 指纹。

一次题集只有第一次冻结候选运行可以称为盲测：

1. 先冻结题集 SHA、候选指纹、唯一指标门槛和红线；
2. 不把事实标签发给被测系统；
3. 第一次运行后保留原始结果，不删题、不放宽门槛；
4. 已揭晓题目只能作为回归集；
5. 如果修复失败样本，下一次未知验证必须新建 v2 密封集，不能把同一 v1 反复调到 100% 后再称为盲测。

## 当前真实结果

零费用 `Hash + BM25 + RRF + Extractive` 对照已经首次运行：严格通过 `14/25`，端到端有据回答成功率
为 **56%**，质量门 `FAIL`。其中 5 道可回答题遗漏至少一个必要事实，6 道知识缺口题全部被相似资料
带偏并自动回答，触发零容忍红线。脱敏结果保存在
`data/evaluation/results/grounded_answer_success_v1_offline_baseline.json`。

首次千问冻结候选已经运行：严格通过 `10/25`，端到端有据回答成功率为 **40%**，质量门 `FAIL`。
它在 6 道知识缺口题中正确拒答 5 道，明显优于 Extractive 的 `0/6`；但 19 道可回答题只有 5 道完整
覆盖全部必要事实，14 道至少遗漏一项。没有出现禁止事实，也没有非法或无支持引用；唯一红线是对“过保
清灰和换硅脂是否免费、每年几次”这条知识缺口仍然自动回答。

这不等于“千问所有能力都比 Extractive 差”。Extractive 通过复制整段候选证据更容易碰齐关键词，却会对
所有知识缺口强行回答；千问更会拒答，但简洁改写经常省略次要条件。首次结果已保存在
`data/evaluation/results/grounded_answer_success_v1_frozen_result.json`，不能覆盖或美化。由于脱敏报告刻意
不保存模型答案正文，下一步需要使用本机私有诊断报告区分真实漏答与同义表达未命中；同一 v1 复跑只能
标记为回归。

揭晓后的人工标签审计还发现：14 道“必要事实缺失”中约 8 道确实漏了用户直接询问的核心结论，另有约
6 道的缺失项更像背景、重复结论或可选流程说明。由于首次运行没有保存原始答案，不能据此正式重算，
更不能把示意修正当成新指标。公开的 40% 继续作为 v1 严格口径首次结果；后续私有诊断应把失败分成
`MODEL_OMISSION`、`MATCHER_FALSE_NEGATIVE`、`GOLD_SCOPE_TOO_STRICT` 和
`AMBIGUOUS_NEEDS_REVIEW` 四类，再用新的 v2 密封集给出未知样本结论。

## 私有 REGRESSION 诊断怎么运行

首次 `10/25（40%）` 是已经冻结的公开事实。私有诊断的作用只是保存足够的本机材料，帮助解释每条失败，
**不会覆盖首次结果，也不能把同一套 v1 重新包装成新的盲测**。

私有诊断只能使用下面这一组完整参数，不能省略其中任何一个：

```powershell
uv run python examples/34_grounded_answer_success_experiment.py --confirm-blind --confirm-paid-api --regression --write-private-diagnostics
```

这条命令会再次调用真实千问 Embedding 和聊天模型，因此会产生新的付费请求。它必须由项目所有者本人
看清参数后主动运行；本项目的自动化流程和助手都不能代为执行。实际请求次数和费用以当次输出为准。

私有诊断会保存问题、模型原始回答、Top-K 候选与实际引用、逐事实匹配明细等人工复核所需材料。文件固定
写入：

```text
data/private_evaluation/diagnostics/grounded_answer_success
```

这个目录被 Git 和 Docker 构建上下文共同忽略。即使文件看起来只是 JSON，其中仍可能含有私有题目、答案
和完整证据，**不要把它提交到 GitHub、放进镜像、粘贴到公开聊天或发送给无关人员**。

人工复核时，每条失败归入下面四类之一：

| 分类 | 大白话解释 | 下一步 |
|---|---|---|
| `MODEL_OMISSION` | 证据足够，模型答案确实漏了用户需要的关键事实 | 优化回答提示、回答结构或生成后的完整性检查 |
| `MATCHER_FALSE_NEGATIVE` | 模型其实表达了该事实，只是换了一种说法，机械匹配器没有认出来 | 补充同义表达或改进匹配器，不改模型 |
| `GOLD_SCOPE_TOO_STRICT` | 金标把用户没有直接询问的背景或次要说明也设成了必答项 | 修订下一版金标范围；首次40%仍不重算 |
| `AMBIGUOUS_NEEDS_REVIEW` | 当前材料不足，或多人可能有不同判断 | 暂不改代码和金标，交给第二位人工复核 |

运行结束后，用户只需回复“运行完成”。项目文件就在同一台电脑上，可以继续从上述私有目录读取并分析；
不需要把诊断 JSON 复制到聊天中，更不需要公开上传。

## 在 PyCharm 中运行

三个配置都使用相同基础设置：

- Script path：`D:\serviceops-agent\examples\34_grounded_answer_success_experiment.py`
- Working directory：`D:\serviceops-agent`
- Python interpreter：`D:\serviceops-agent\.venv\Scripts\python.exe`

只修改 **Parameters**：

| 模式 | Parameters | 会发生什么 |
|---|---|---|
| 1. 安全预检 | 留空 | 只展示题量、SHA、候选指纹和费用计划；不读取私有题目，不调用千问 |
| 2. 零费用密封集对照 | `--confirm-blind` | 校验并读取密封集，运行 Hash + BM25 + RRF + Extractive 对照；不调用千问 |
| 3. 历史首次真实候选 | `--confirm-blind --confirm-paid-api` | 首次结果已存在；保留该行用于解释历史运行方式，不应再把复跑称为首次盲测 |
| 4. 私有回归诊断 | `--confirm-blind --confirm-paid-api --regression --write-private-diagnostics` | 再次产生付费请求；保存仅供本机人工复核的详细诊断，不覆盖首次结果 |

第三种模式要求本机 `.env` 已正确配置千问 Key 和地域匹配的 Base URL。脚本预估最多 4 次 Embedding 请求、
25 次聊天调用；最终以实际报告为准。

首次真实结果已经存在后，普通回归复跑至少要明确标记：

```text
--confirm-blind --confirm-paid-api --regression
```

回归模式不会覆盖首次冻结结果，也不能再称为一次新的盲测。
如果需要写出包含原始回答和证据的私有诊断，则必须再加
`--write-private-diagnostics`，即使用表格第 4 行的完整参数。该开关不能单独使用。

## 怎样解释结果

如果通过，可以说：

> 我在候选和门槛冻结后，用 25 道密封题做了一次事实级端到端验收。每题只有全部关键事实正确、
> 实际引用切片能支持这些事实、没有禁止结论，或知识缺口正确拒答时才算通过。最终数字只代表这套
> 冻结语料、候选和一次性题集，不代表线上所有问题的准确率。

如果失败，也要保留失败结果，并按错误码判断是范围、检索、拒答、关键事实还是引用支持问题。修复后的
同题结果只能叫回归结果；新的效果结论需要另一套从未揭晓的密封集。
